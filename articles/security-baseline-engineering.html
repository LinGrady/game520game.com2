Building Security Baselines Developers Will Follow

By James Chen Published May 6, 2026 Updated May 6, 2026 12-16 min read

Security baselines fail when they are written like commandments and delivered like paperwork. Developers do not reject baselines because they dislike security. They reject baselines when the requirements are unclear, slow, inconsistent with delivery tools, or disconnected from the way software is actually built. A useful baseline is an engineering product: versioned, tested, measured, maintained, and improved through feedback.

I think of a baseline as the minimum acceptable path for building and running a service. It should answer practical questions about secrets, logging, dependency sources, network exposure, runtime settings, and exceptions. The more these answers are encoded into templates and platform defaults, the less teams have to remember.

The security problem

The security problem is inconsistent execution. One team encrypts sensitive storage, another leaves the setting to a manual checklist. One service uses managed identity, another stores a long-lived token. One repository follows dependency review, another downloads packages during deployment. These differences are usually local decisions made under time pressure without a shared secure path.

Baselines also age. A control that was reasonable two years ago may be weak today, while a control that sounded advanced may prove too expensive to operate. If nobody owns baseline maintenance, teams accumulate exceptions and security leaders lose credibility.

Why generic advice fails

Generic advice says to enforce secure coding standards, require reviews, scan builds, and harden infrastructure. Those are useful categories, but developers need specific defaults. Which scanner matters? Which finding blocks a release? Which logging fields are required? Which infrastructure module is approved? A broad policy creates debate at the exact moment a team is trying to ship.

Generic advice also treats enforcement as the first step. If enforcement arrives before enablement, it creates resentment and delay. Give teams a service template with baseline controls already present, a dependency workflow connected to review, and deployment rules that explain failure clearly.

The engineering control model

My baseline model has three layers: defaults, checks, and exceptions. Defaults are the preferred implementation: templates, modules, starter repositories, logging libraries, identity patterns, and deployment workflows. Checks verify that the default remains intact and should be automated where possible. Exceptions handle cases where the default does not fit, with owner, reason, compensating control, and expiration.

Each baseline requirement should have a threat it reduces, an implementation path, an owner, a verification method, and a support channel. Version the baseline so teams know what changed, when enforcement begins, which services are grandfathered temporarily, and how migration will be supported.

Signals worth measuring

Measure baseline adoption by service criticality, not only by repository count. Track control failures by requirement so you know whether teams are struggling with one specific module, one unclear rule, or one unsupported use case. Measure exception volume, exception age, and exception renewal rate. These show whether the baseline is practical.

Another signal is developer time to compliance. If a new service takes days to satisfy routine baseline requirements, the platform needs improvement. Watch for repeated manual evidence collection, unclear pipeline errors, and recurring questions in support channels.

Review checklist

  • Write each baseline control with a threat, implementation path, verification method, owner, and support channel.
  • Provide approved templates, modules, and libraries before enforcing broad requirements across product teams.
  • Automate checks where the result is objective and give developers failure messages that explain the fix.
  • Version the baseline and publish migration windows for new or changed controls.
  • Track exceptions with owner, reason, compensating control, expiration date, and review history.
  • Use developer feedback and support tickets to improve the baseline as an internal product.

Final recommendation

Build security baselines like platform products. Start with controls that reduce common, high-impact risk and can be delivered through reusable defaults. Make requirements specific, testable, versioned, and supported.

Developers will follow baselines when the secure path is clear, reliable, and faster than inventing a local alternative. That is the difference between a document people acknowledge and a standard the engineering system actually uses.

A practical program also assigns maintenance work after the review. Each gap should become either a platform improvement, a product-team task, a documented risk decision, or an obsolete requirement that should be removed. This prevents reviews from becoming recurring conversations with no engineering change. The best security organizations treat every review as a chance to reduce future manual effort, clarify ownership, and make the safest path easier for the next team that faces the same decision. Baselines earn trust when teams can see that feedback changes the standard over time, enforcement messages improve, and repeated exceptions become roadmap input instead of permanent delivery friction.
