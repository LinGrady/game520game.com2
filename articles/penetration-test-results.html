What Our Penetration Test Actually Found: A Real Security Analysis

👤 Elena Rodriguez 📅 March 20, 2026 ⏱️ 12 min read
Advertisement

Six weeks ago, we hired a professional security firm to hack our systems. Not because we suspected we were compromised, but because we wanted to find our vulnerabilities before the bad guys did.

The results were humbling. They found 7 security issues, including 2 critical vulnerabilities that could have allowed a skilled attacker to access our entire customer database. In this article, I'm sharing what they found, how we fixed each issue, and what you can learn from our mistakes.

Critical Finding #1: SQL Injection in API Endpoint

Our search API was vulnerable to SQL injection. This was embarrassing—SQL injection has been a known vulnerability for over 20 years, and we still had it.

What They Found

The testers sent this payload in the search parameter:

            
search='; DROP TABLE users;--

And our database executed it. The tester was able to:

  • Extract our entire user database (names, emails, hashed passwords)
  • Modify data in our database
  • Execute system commands on our database server

How We Fixed It

We implemented parameterized queries (also known as prepared statements). Here's the before and after:


# BEFORE (Vulnerable)
def search_users(query):
    sql = f"SELECT * FROM users WHERE name LIKE '%{query}%'"
    cursor.execute(sql)

# AFTER (Fixed)
def search_users(query):
    sql = "SELECT * FROM users WHERE name LIKE %s"
    cursor.execute(sql, (f'%{query}%',))

Lesson Learned

Never, ever concatenate user input into SQL queries. Use parameterized queries or an ORM. This vulnerability should never exist in any modern application.

Critical Finding #2: Broken Authentication

Our password reset functionality had a critical flaw. After requesting a password reset, the verification token was predictable and didn't expire properly.

What They Found

  • Password reset tokens were based on user ID + timestamp (predictable)
  • Tokens didn't expire for 72 hours
  • No rate limiting on password reset requests

The tester created a script that could reset any user's password within minutes.

How We Fixed It

  • Implemented cryptographically secure random tokens (32 bytes, using secrets module)
  • Reduced token validity to 15 minutes
  • Added rate limiting: max 3 reset requests per hour per email
  • Added email notification when password is reset

High Finding #1: Sensitive Data in Logs

Our application logs were containing sensitive information that shouldn't have been there.

What They Found

The testers analyzed our log files and found:

  • Full credit card numbers in API logs (from payment processing)
  • API keys and secrets in application logs
  • User email addresses and partial passwords in debug logs

How We Fixed It

  • Implemented log filtering to mask sensitive fields
  • Set up automated log review to detect sensitive data
  • Created strict log retention policies (90 days max)
  • Moved to a centralized logging system with access controls

High Finding #2: Insecure Direct Object References (IDOR)

We had a common vulnerability where users could access other users' data by simply changing an ID in the URL.

What They Found

For example, if User A visited:

            
https://ourapp.com/api/users/123/profile

They could change "123" to "124" and access User B's profile—without any authentication.

How We Fixed It

  • Implemented proper authorization checks on every API endpoint
  • Added user context validation (does this user have access to this resource?)
  • Implemented indirect references (mapping internal IDs to random tokens)

High Finding #3: Missing Security Headers

Our web application was missing several important security headers that protect users from common attacks.

What They Found

Our server wasn't sending:

  • Content-Security-Policy (prevents XSS)
  • X-Content-Type-Options (prevents MIME sniffing)
  • Strict-Transport-Security (enforces HTTPS)
  • X-Frame-Options (prevents clickjacking)

How We Fixed It

We added these headers to our web server configuration:


# Nginx configuration
add_header Content-Security-Policy "default-src 'self'";
add_header X-Content-Type-Options "nosniff";
add_header Strict-Transport-Security "max-age=31536000";
add_header X-Frame-Options "DENY";

Medium Finding: Information Disclosure

Our API was revealing too much information in error messages.

What They Found

When our API encountered an error, it displayed full stack traces, database connection strings, and internal file paths. This information could help attackers understand our system architecture.

How We Fixed It

  • Implemented custom error pages for production
  • Set DEBUG=False in production
  • Created generic error messages for users, with detailed logs only for administrators

Low Finding: Verbose HTTP Methods

Our server responded to HTTP TRACE, which could be used in cross-site tracing attacks.

How We Fixed It


# Disable TRACE method in Nginx
if ($request_method = TRACE) {
    return 405;
}

What We Changed in Our Development Process

Finding these vulnerabilities was a wake-up call. We've since implemented several changes:

  1. Security code review: Every code change now goes through security review
  2. Automated scanning: We run automated security scans on every deployment
  3. Dependency scanning: We check for vulnerable dependencies weekly
  4. Annual penetration testing: We'll hire professionals to test us yearly
  5. Security training: All developers now complete annual security training

Key Takeaways

  1. Hack yourself before someone else does: Regular penetration testing is essential
  2. Don't assume your code is secure: Even experienced developers make mistakes
  3. SQL injection is still common: It's 2026 and we still found it
  4. Authentication matters: Don't cut corners on password reset flows
  5. Logs can be dangerous: Be careful what you log
